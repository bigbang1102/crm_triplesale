## 0. TL;DR — things the Angular design must know first

1. **Almost nothing in this group is classic JSF any more.** The "live" pages are `.xhtml` shells whose behaviour is a big inline script or `resources/support/*.js` calling same-origin servlets with `fetch()`. Only the 7 "ข้อมูลประกอบ" document pages (`sales_document*.xhtml`, `sales_document_sub_*.xhtml`) and some legacy pages (petition, old quotation, market-plan v1, promotion v1, old chat dialog) are still real JSF/PrimeFaces components bound to beans.
2. **Sales documents have 3 very different maturity levels**: (a) RV ใบรับเงิน = fully wired to backend (create / list / detail / approve / print / attach); (b) QT ใบเสนอราคา, BK ใบจอง(=ใบสั่งขาย), OB ใบส่งสินค้า, AQ ใบเสนอราคารถยนต์, AD ใบจองรถยนต์ = **complete UI + client-side calculation + print preview, but NO save API** ("ยังไม่เชื่อมต่อ"; their list tables are always empty); (c) "ข้อมูลประกอบ" 7 documents = real backend (`/api/v1/documents?formType=`).
3. **Active navigation is driven by URL params** (`pid, page_id, act, acts, sub_id, action_type, navbar_menu`) + server session (`ss_param_navbar`) + role keys (`hasFeature('FEATURE_CRM_*')`). Angular must replace with route data + a permission service (key list in §1.4).
4. **All backend access goes through war proxy servlets** that add `Authorization: Bearer` from the HTTP session (`/board/*`, `/rvapi`, `/chat-api/*`, `/socket.io/*`, `/ai-api/*`, `/help-api/*`, `/aihub/*`, `/aitran*`, `/docproxy`, `/docattach`, `/rvreport`, `/rvreceipt`, `/report-pdf`). Decide BFF vs direct-Bearer early.
5. **Two risky leftovers in the repo (do NOT port, do not copy values):** `web/dev.xhtml` has ~30 hard-coded `loginsso?ssousername=…&ssopassword=…` links (plain-text credentials); `market_plan_land.xhtml`, `market_plan_map_land.xhtml`, `chat/index_1.xhtml`, `chat/index_2.xhtml` embed a Google Maps API key in a script tag. Recommend rotating/removing; never copy into Angular.
6. **Root-level `web/*.xhtml` (about 45 files) are the PrimeFaces Pandora showcase** (blocks, button, charts, crud, table, formlayout …) = template demo, not product. Confirmed: the only menu linking to them is `WEB-INF/pages/ungroupedMenu.xhtml`, rendered only when `guestPreferences.groupedMenu=false`; default is `true` (`GuestPreferences.java:50`). Exception: `web/index.xhtml` is the real **login page**.

- Active-item highlight: JS in groupedMenu matches the `navbar_menu` param against each link; falls back to page file name, then to `sessionStorage['menu_navbar']` (so child pages keep the parent highlighted). Angular: route `data.menuKey`.
- Topbar visibility per group is computed server-side by `CommonBean.viewTopbarPage()` (map navbar_menu to a list of `topbar-page-NNN`); an unknown group (e.g. `navbar_menu_sale`) returns true for all panels, so sales pages **hide all panels by JS** and inject their own tab strip (`components/sales_doc_tabs.xhtml`, element `#sd2TopTabs`). AI HUB hides non-AI panels by inline CSS.
- URL param protocol: `pid=1&page_id=N&act=N&acts=NN&sub_id=N&action_type=list|add|edit|detail|view&navbar_menu=…` — `act` sets `menu_active`, `acts` sets `menu_active_sub` (CommonBean lines 205-219). `ss_param_navbar` remembers the last navbar_menu in the session.

### 3.9 Lifecycle / status flow
- **RV**: create → `new/new1` ("ใหม่", filter "สร้างเอกสารใหม่") → (async flow `waitToFlow` "รอเข้าระบบ") → user clicks **อนุมัติ** (needs role; modal requires selecting รูปแบบเงื่อนไข) → `ActionWaitProcess` ("กำลังอนุมัติ", locked) → `active1/active2/active` ("ใช้งาน"; filter "ตัดหนี้แล้ว"). `cancel` = "ยกเลิก". No edit / delete after create. ERP sync adds `print_forms` / `erpSynced`; unsynced RVs print a CRM-made preview instead of RV-01.
- **QT / BK / OB / AQ / AD**: no persisted lifecycle yet. Old mock list used statuses "รออนุมัติ" / "ปิดเอกสารแล้ว". Intended chain QT → BK → OB → RV (references, not enforced client-side). BK = "ใบสั่งขาย".
- **Supporting docs (CA/CS/LA/CP/PC/LAF)**: `new` "สร้างใหม่" → `WAIT_APPROVE` "รออนุมัติ" → `ACTIVE` "สำเร็จ" / `REJECTED` "ไม่อนุมัติ" / `cancel` "ยกเลิก" (badge CSS `status-new / status-pending / status-success / status-rejected`). `statusActionButton` exists in the bean (approve action not surfaced in the pages read).

## 14. The 10 most complex behaviours / risks

1. **Sales-document calculation engine** (`sales_doc_items.js` + `sales_doc_payment.js` + `sales_doc_auto.js` + finance): VAT include/exclude/exempt *per row*, grouped by mode with the extra discount allocated proportionally, discounts as amount or %, schedule/deposit/prepaid tables that must equal or not exceed the total (and warn when the VAT mode changes), flat-rate instalments, down-payment amount and % kept in sync both ways. Port with unit tests against the formulas in 3.6/3.8 and keep rounding identical (round2 + EPSILON, en-US formatting).
2. **RV create semantics**: backend/ERP expects *pre-VAT* `value` (Incl. rows divided by 1.07 at full precision), payer must be an ERP CUS code, branch mandatory, credit-card/transfer amounts locked to the remaining due, change calculation, base64 attachments inline in the create call, async persistence (green/orange/red result states), the `verify` object, approve returns HTTP 200 with the real outcome hidden in `result.hopDone`, 7 raw statuses including the transient `ActionWaitProcess`, ERP number vs CRM number for printing (RV-01 only after ERP sync).
3. **Five document types with no backend** (QT/BK/OB/AQ/AD): build as local-state forms behind a pluggable `DocumentRepository` (stub now) so wiring the API later is one class; reference picking (`SalesDocRef` SOURCES) and document search are stubs too; attachments currently go to the *prospect* record, not the document; the company header is hard-coded; vehicle masters are mock JSON. Product decisions are needed before a real build.
4. **Print/preview pipeline**: iframe copy of the paper with flattened inputs, formal print layout (`.dp-*`, `@page`), Thai baht-in-words, an auto-dealer variant. Recreate with a dedicated print-template component plus `window.print()` or server PDF, and decide who owns the legal text (AD terms 10.1-10.2).
5. **Permission model**: key names are inconsistent (FEATURE_CRM_*, CRM_RV_*, CRM_Document_X_*, Chat_*, MODULE_*), several gates use a wrong/guessed key (promotion and petition use `CRM_Prospect_View`; RV uses `FEATURE_CRM_Document` because the tenant has no `CRM_RV_*`), and some pages have no page-level rule at all (any logged-in user can open the QT/BK/OB/AQ/AD forms, the type list, `sales_document_sub_1`, ai_hub, ai_translator). Define one permission map in Angular and mirror the server rules.
6. **Chat realtime**: Socket.IO polling through a proxy, optimistic sends with `clientMessageId`, de-dupe/upsert of socket + REST messages, per-user stars, room join, re-sync on reconnect (merge, never overwrite), timestamp units (socket seconds vs ISO, fixed 19/10), 5 channels with several accounts each, 3-level bot switch (global AND (room ?? page)), media proxy URLs, 5 settings modals with secrets (never echo tokens), analytics-AI panel with long calls (about 80 s) and hand-drawn SVG charts (use one chart library instead).
7. **AI HUB / translator long jobs**: multipart uploads with progress (XHR), 6-minute server timeout, polling only while a job is translating and the tab is visible, status machine with server-side 409 conflicts, client-side parsing of Thai date strings sent by the server (fragile), embedded draw.io editor, token/usage accounting, localStorage histories keyed to the session.
8. **Prospect master form (570 KB)**: three tabs, about 300 fields with conditional panels (individual vs organisation), address cascades (province, district, sub-district, postcode), `data-col` driven collection into `extraInfo`/`satisfaction`, date-format conversions, add/view/edit modes, 5 confirm dialogs, avatar rules, lead creation with the auto-assign-to-Social-Admin rule. Model it as typed reactive forms with section components; the survey (Q6/Q7 Y/N groups) needs special mappers.
9. **Auth/session**: the token lives only in the server session and proxies attach it; JSON 401 + global popup; `?auth=NO_TOKEN|TOKEN_EXPIRED` bounce and loop avoidance; multi-company login (ORG_REQUIRED) and the super-admin "no company chosen" 409 on branches; roles as OR-lists. In Angular the BFF/token decision affects every service in this report.
10. **Secrets and styling debt in the repo**: `dev.xhtml` credentials and Google Maps keys in 4 legacy pages (do not port); per-page inline CSS plus a 58 KB global `dark_mode.css` and hard-coded colours (`#35236A`, `#F0F2FF`, `#1F2430` ...) — extract design tokens early.
Also worth noting: i18n is split (message bundles vs hard-coded Thai in AI / petition / market-plan pages); users expect drag-scroll tables, sticky headers and skeletons; every page carries a dark-mode block.
